# 参考：播放页底部行高（集数 / 详情 / 域名）

> 口径文档，不改代码。维护人：Hermes（W106）。
> 记录「计划 32、实测 44」这条分叉为什么这样结案，避免下一次改播放页时又把 44 悄悄压回 32。

## 一句话

**底部三段行保持行高 44（触摸热区），不压到 32。** 今后任何人动这一行，报数时必须同时给两个数：
**热区尺寸**与**视觉高度**——只说「行高 32」不算交代清楚。

## 1. 3.0.13 拍定值（计划）

`docs/release-notes/v3.0.13.md:42`：

> 底部「集数 / 详情 / 站点域名」改为固定三段：集数胶囊定宽 88、详情 `flex-1` 单行省略、域名隐藏时保留占位；**行高 32**、**段间距 8**。

所以 3.0.13 的设计口径是：

| 项 | 拍定值 |
|---|---|
| 行高 | 32 |
| 段间距 | 8 |
| 左段：集数胶囊 | 定宽 88，文字超出省略，不推动别人 |
| 中段：详情 | `flex-1`，单行省略 |
| 右段：站点域名 | 占位固定宽（隐藏时 `visibility` 保留宽度，不可点、无热区） |

## 2. 现状实测（实跑数据，不是估算）

实现落在 `src/features/playback/EpisodePlayer.tsx:2492-2493`：

```tsx
<div className="mobile-video-meta-copy relative z-30 flex items-center"
     data-hg-control="meta-bar"
     style={{ paddingRight: 76, pointerEvents: "auto", gap: 8, height: 44 }}>
```

三个子段各自也钉 44（`EpisodePlayer.tsx:2495` / `:2532` / 域名段）。

`pnpm test:player-v3013`（真组件 + 真 CSS，只 mock Tauri IPC）在 **360×640** 视口量到的 bbox：

| 元素 | x | y | w | h |
|---|---|---|---|---|
| 集数胶囊 `第 1/5 集` | 16 | 514 | 88 | **44** |
| 详情 | 112 | 514 | 44 | **44** |
| 站点域名（占位宽） | 194.09 | 514 | 89.91 | **44** |
| 控件层 `bar` | 0 | 508 | 360 | 118 |

段间距实测 `112 − 16 − 88 = 8`，与拍定值一致；**只有行高是 44 而不是 32**。
同一次实跑还验证了「集数变长（`第 1/5 集` → `第 1/120 集`）时详情 x/y、域名 x 不动」，即三段防跳的初衷没有因为行高变化而失效。

### 为什么是 44

3.0.13 之后这一行并入了同一片控件层（`data-hg-control="meta-bar"`），层里还有「全屏观看」入口——它本身就是一行 **44 高、整行可点**的按钮（`EpisodePlayer.tsx:2278-2281`，位置在视频画面底边再往下 8px）：

```tsx
style={{
  top: `calc((var(--vp-h, 100vh) + var(--vp-w, 100vw) * ${srcAspect.toFixed(4)}) / 2 + 8px)`,
  height: 44,
}}
```

一行 44 高的可点按钮挨着一行 32 高的可点文字，会出现「同一片区域里两种热区高度」：
手指按在 32 那段的两侧边缘落空、又因为两行只差 8px 而更容易点错。于是实现时统一按
**44 = 移动端触摸热区下限**（`min-h-11`）取值，代码注释也写明了这个选择：
「行高沿用现状 44（= min-h-11 热区），位置与改前逐像素一致」（`EpisodePlayer.tsx:2490`）。

## 3. 结论：保持 44

- 44 是移动端触摸热区的公认下限（iOS HIG 44pt / Material 48dp，取小者 44 CSS px 为我们的下限）。
  这一行里的三段**全部可点**（选集、详情与标签、线路切换），压到 32 等于把可点区域砍掉 27%，
  是「看着更精致、实际更容易点空」的典型取舍。
- 32 的唯一好处是视觉更收敛，但这一行压在视频画面上，靠 `hg-ov-shadow-strong` 阴影保证可读性，
  44 与 32 的观感差异远小于热区差异。
- 因此**结案：保持 44**。若将来确实要把视觉高度做成 32，必须同时给出两个数（热区仍是 44 的
  透明外扩也算一种做法），并在验收用例里量到这两个数，不允许只报一个「32」。

## 4. 顺带记一条待拍定项（本轮不改）

**竖版片源 `object-fit: cover` 会横向裁掉 17.9%，当前保持现状。**

- 依据：`EpisodePlayer.tsx:2198` — `fit={isDesktop ? "contain" : (portraitVideo && !fs && !vpLandscape) ? "cover" : "contain"}`。
  竖版片源在竖屏非全屏时走 `cover`（为了不留黑边）。
- 算法：9:16 片源（如 1080×1920）铺进 390×844 视口（比 9:16 更细长），`cover` 按高度缩放
  `844 / 1920 = 0.4396`，铺开宽度 `1080 × 0.4396 = 474.7`，视口只有 390，
  横向被裁 `(474.7 − 390) / 474.7 = 17.85% ≈ 17.9%`。
- 现状判断：**保持现状**。改成 `contain` 会在这种机型上下留黑边（观感更差，且用户已按其拍过版），
  改成按宽度铺满则上下溢出。要动的话需要先拍定「宁可裁画面还是宁可留黑边」，属于产品口径，不是 bug。
- 触发条件写清楚，免得下次误判成回归：只有**竖版片源 + 竖屏 + 非全屏 + 视口比 9:16 更细长**时才会裁；
  横版片源、全屏、横屏舞台都走 `contain`。
